# Fixes, 2026-08-07

Changes made to this tree on 2026-08-07, why, and how to check they still hold.
Read alongside `FORK.md`, which describes what this fork adds over upstream.

Every edited file has a `.orig` beside it. Rollback image: `bookorbit:rollback-20260806`
(`docker tag bookorbit:rollback-20260806 bookorbit:merged`, then `docker compose up -d`
from `/opt/bookorbit`). Deployed as `bookorbit:merged-v12`.

## The theme

Every fault below was a feature that had been built to ~90% and left
unconnected. Not one was a design problem, and none of them were visible as
errors — they all presented as something quietly empty.

## 1. The sidebar rendered nothing

`SidebarNavItem.vue` declares `to: RouteLocationRaw` as required and renders
`<RouterLink :to="to">`. `AppSidebar.vue` navigates by click handler and passes
**no `to`** on any of its 8 nav items, because `navigateFromSidebar()` also has
to close the mobile drawer. So every item rendered `<RouterLink :to="undefined">`,
`router.resolve(undefined)` threw mid-render, and the whole list died.

Sections with no items looked fine — an empty section renders its "none yet"
text and never constructs a nav item. Only sections **with** content broke,
which is why Libraries appeared blank while Smart Scopes and Collections
looked healthy.

`to` is now optional: a route renders a `RouterLink`, no route renders a
`<button>`. Existing click handlers are untouched.

## 2. "Your library is empty" on a 348k catalogue

`DashboardView.vue` called `useLibraries()` **without** `includeSourceBacked`,
so it read the filesystem-only cache — genuinely 0, because every book lives in
the warehouse catalogue. `hasNoLibraries` was permanently true.

## 3. Both dashboard catalog shelves 400'd

The client called `/dashboard/scrollers/catalog-additions` and
`/scrollers/catalog-discovery`. The server refuses those on the generic
endpoint **by design** — its own test asserts *"Library discovery is loaded
through the library discovery endpoint"*. They have dedicated routes
(`/dashboard/catalog-additions`, `/dashboard/catalog-discovery`), which the
client now uses.

## 4. Raw i18n keys on screen

Three keys were referenced by upgraded components and defined in **no** locale
file: `components.sidebar.tagline`, `components.sidebar.supportShort`,
`components.sidebar.libraryScanning`. Later, `dashboard.settings.shelfNames.undefined`
appeared because `SCROLLER_TYPE` gained `catalog-additions` and
`catalog-discovery` but `SHELF_NAME_KEYS` did not.

That map is typed `Record<ScrollerType, ShelfNameKey>` and **should** have
failed compilation. The image builds the client with `vite build` and no
`vue-tsc`, so nothing checked it. The server build *does* typecheck (`nest build`
rejected two of my own errors). **Worth fixing: add `vue-tsc` to the client build.**

`tagline` is set to "Personal reading library" — invented wording, since no
locale ever defined it. Change freely.

## 5. Statistics: four SQL bugs

- `metadataScoreDistribution`, `libraryMetadataCompleteness` — a parameterised
  `sql` fragment reused in both `select` and `group by` gets **different
  placeholder numbers** ($1…$11 vs $12…$22), so Postgres sees two expressions
  and rejects the query. Now grouped/ordered **by ordinal**.
- `storageByFormat`, `largestBooks` — `COALESCE(format, media_type)` mixes
  varchar with the `warehouse_media_type` enum. Now `media_type::text`.
- `largestBooks` also read `warehouse_catalog_details` without joining it.

`metadata-completeness` and `library-metadata-completeness` now return 200.
`storage-by-format`, `largest-books` and `metadata-score-distribution` now hit
the 30s `statement_timeout` instead — a performance problem, see §8.

## 6. Interrupted syncs were never reconciled

`reconcileRunningSyncRuns()` existed and worked, but was reached **only** from
`getSyncState()` — the admin status page. So a run interrupted by a restart sat
`running` forever unless somebody happened to look. Restarting is the ordinary
way a sync is interrupted.

Now also runs on `onModuleInit`, wrapped so a reconcile failure cannot block
boot.

## 7. No item had a genre or a narrator — two separate causes

`genres` and `narrators` were empty for **all 348,474** items, with indexes
built on both.

**Cause A — nothing fetched detail.** The catalog sync stores the warehouse's
*list* projection, which carries no genres, narrators or chapters. Those come
from `GET /audiobooks/{id}` and `GET /books/{id}`. `warehouse_catalog_details`
and `repository.upsertCatalogDetail()` were built for exactly this — and
`upsertCatalogDetail` **had no callers at all**. The table was empty for the
instance's whole life, and `getAudiobook()` returned `{ chapters: [], files: [] }`
every time.

**Cause B — the mapper discarded them anyway.** `listValue()` kept only
`typeof entry === 'string'`. The warehouse returns
`[{ id, name, slug }]` objects, so every genre and narrator was silently
filtered out. **A full re-sync would not have fixed this**; it now reads
`name`, falling back to `title`/`value`.

Fixing A alone looked like success — the detail cache filled while every item
still had `[]`. Check the item rows, not the cache.

New: `getAudiobookWireDetail()` / `getBookWireDetail()` return the response
**unmapped**, because `raw_payload` is read back through mappers that expect the
warehouse's field names. Caching the mapped form would round-trip into
something unreadable.

### Backfill

`POST /api/v1/admin/warehouse/catalog-detail-backfill/{audiobooks,ebooks}?limit=N`
(superuser, N capped at 500). Bounded and resumable — "has no cached detail"
*is* the queue, so there is no cursor to corrupt.

It reports `facetsBefore`/`facetsAfter` and a **`stalled`** flag: details
fetched but no item enriched. Stop and investigate if you see it; both bugs
above looked like success from the outside.

`/root/bo-backfill.sh {audiobooks|ebooks}` drains it, logging to
`/var/log/bo-backfill.log`. **It reuses its token on purpose** — re-logging in
per batch hits the login endpoint's 5-per-minute throttle and kills the drain
after three batches.

## 8. Statistics performance — three causes, not one

`storage-by-format`, `largest-books`, `publication-year-timeline`,
`metadata-completeness`, `library-metadata-completeness` and
`acquisition-lag-scatter` all returned 500 or took 8-20s. All six now answer in
**single-digit milliseconds**. Three separate things were wrong:

**Derived size, recomputed per row.** Audiobooks carry no top-level file size —
the warehouse's `Audiobook` model has only per-file rows — so the expression ran
a correlated subquery over `jsonb_array_elements(raw_payload->'files')` for each
of ~184,000 rows. **No index can fix that**: Postgres cannot index an expression
containing a subquery. Migration **0048** adds `file_size_bytes`, backfills it
(159,150 ebooks / 356 GB, 184,500 audiobooks / 51 TB), and the mappers now
compute it once at sync time. `catalogFileSizeExpression()` reads the column
first; COALESCE is lazy, so the laterals are never evaluated once it is
populated.

**/dev/shm was 64MB** — Docker's default. `metadata-score-distribution` was not
slow, it was dying: *"could not resize shared memory segment ... No space left
on device"*. Now `shm_size: 2gb`.

**Postgres was on stock settings** — `shared_buffers` 160MB, `work_mem` 4MB,
`random_page_cost` 4 (a spinning-disk assumption on an NVMe host),
`max_parallel_workers_per_gather` 2. Tuned in compose for 8 cores / 8GB. This
is what turned the 8-19s queries into milliseconds: the working set now fits in
cache. **Re-tune `shared_buffers`/`effective_cache_size` if the host changes.**

## 9. Audiobookshelf compatibility — verified

Exercised the full handshake against the live instance, which is as far as this
goes without a physical device:

    GET  /ping    200  {"success":true}
    GET  /status  200  {"server":"BookOrbit","authMethods":["local"]}
    POST /login   200  token at the TOP level (user.token is null — clients
                       read the top-level one)
    GET  /api/libraries                    200  3 libraries, correct mediaType,
                                                Audiobooks coverAspectRatio 1/1
    GET  /api/libraries/{id}/items         200  0.21s, correct item shape,
                                                narrators populated

**One real gap: `duration` is always null on source-backed items.** BookCard
has no duration — it lives on AudioMetadata, which the browse projection does
not carry — so `mapAbsLibraryItemsPage` hardcodes null. Audiobookshelf clients
therefore show no length and cannot render a progress position. All 184,500
audiobooks have `duration_seconds` in warehouse_catalog_items; fixing this means
threading it into the browse projection, not editing the mapper.

Still not done: pairing an actual client (Plappa / ShelfPlayer / the official
app). The protocol answers correctly, but no real device has authenticated.

## 10. Still open

- **`metadata-score-distribution` still times out.** The only statistics
  endpoint left. It recomputes an 11-term weighted score plus four
  percentile_cont calls over 348k rows on every request. Not resource-bound —
  the same materialise-at-sync-time fix that worked for file size applies.
- **Comics have no `file_size_bytes`.** Their row mapper does not set it, so
  those 4,824 rows fall back to the payload expression. Harmless at that
  volume.
- **Add `vue-tsc` to the client build** (see §4).
- **Ebook detail is fetched but not surfaced** — `getEbook()`'s return type has
  no slot for chapters/files. Facets land on the item row, which is what genre
  browsing reads, so this only matters if you want ebook detail in the UI.
